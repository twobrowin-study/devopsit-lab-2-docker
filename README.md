## Часть 1 | Установка и настройка Docker

Docker является наиболее распространённым средством управления контейнерами. Однако, используется в основном для разработки.

В зависимости от используемой ОС, доступны разные варианты установки Docker.

Наиболее важным требованием Docker является наличие ядра Linux, а также способе взаимодействия с ним.

Для Linux доступны варианты обычной установки, а также установки в rootless (непривилегированном) режиме.

Для Windows и MacOS доступен Docker Desktop - приложение, которые помимо GUI содержит также небольшую ВМ на Linux для запуска Docker.

### Запуск rootless Docker в ALT Linux (на ПК в лабораторных кабинетах)

В лабораторных кабинетах 208х/210х, 306х/308х установлен docker engine rootless.

Установка в таком режиме не требует привилегированного режима доступа к ядру Linux. Основные ограничения сводятся к более медленной работе сетевого слоя (он проходит через дополнительный слой изоляции) и невозможность воспользоваться продвинутыми функциями ядра Linux.

В рамках настоящей лабораторной работы, такого режима установки будет более чем достаточно.

Для активации Docker для пользователя следует выполнить команды:

```bash
# Установка Rootless движка Docker
dockerd-rootless-setuptool.sh install

# Дать доступ к локальному docker сокету
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
```

### Установка Docker в Ubuntu

Современные версии Docker реализуют концепцию разделения API CNCF и зависит от containerd и runc.

Для начала установки в ОС Ubuntu следует выполнить следующие команды:

```bash
# Добавление официальных GPG ключей
sudo apt update
sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Добавление репозитория Docker
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
```

Собственно установка Docker и всех зависимостей:

```bash
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Для того чтобы получить возможность использовать утилиту Docker без указания sudo следует выполнить следующие операции:

```bash
sudo usermod -aG docker $USER

sudo systemctl restart docker

su - $USER
```

Однако, при закрытии терминала, до выхода из сессии пользователя ОС, следует повторять последнюю строчку каждый раз при запуске нового терминала.

### Установка Docker Desktop в Windows и MacOS

Для установки Docker Desktop следует воспользоваться инструкциями, расположенными [по ссылке](https://www.docker.com/products/docker-desktop/).

Для MacOS (и некоторых Windows машин) следует учитывать особенности архитектуры - эти машины имеют архитектуру arm64. Для поддержки amd64 архитектуры будет использована эмуляция в ВМ.

Явное управление тем, для какой архитектуры следует собирать и/или запускать Docker контейнер выполняется флагами `--platform linux/amd64` и `--platform linux/arm64`.

Образы, расположенные в закрытом контуре МГТУ им. Н.Э. Баумана собраны исключительно под платформу `linux/amd64`.

Более комплексный пример управления контейнером является запуск контейнера ОС Ubuntu:

```bash
#‼️ При наличии доступа в Интернет
docker run -it busybox

#‼️ При работе в закрытом контуре МГТУ
docker run -it registry.gitlab.bmstu.ru/devops-dataops-intro/labs/lab-2-docker/busybox
```

Команда запуска включает в себя:

* Флаги `-i` и `-t`, позволяющие использовать интерактивный режим работы и создать виртуальный tty для передачи команд управления ОС контейнера

* Указание на реестр, из которого следует загрузить образ `registry.gitlab.bmstu.ru/devops-dataops-intro/labs/lab-2-docker/` указан явно, а для версии команды с выгрузкой из Интернета, будет подставлено `docker.io/library/`

* Название образа контейнера `busybox` (busybox это набор скомпилированных утилит linux, среди которых будет всё что нам требуется для экспериментов - технически можно использовать образ ubuntu, но потребуется устанавливать ПО в ручном режиме)

* Название выполняемой при старте команды `bash`

Следует заметит, что после запуска контейнера обозначение текущего пользователя и имени хоста будут изменены на `/ #` - обозначение текущей рабочей директории и указания на ввод интерпретатора sh.

Выполним команду получения сведений о текущем хосте:

```bash
cat /etc/hostname
```

Строка, содержащаяся в этом файле является идентификатором контейнера, убедимся в этом выполнив команду **в другом окне терминала**:

```bash
docker ps
```

Будет отображён единственный контейнер в статусе `Up` и идентификатором, полученным выше.

Команда получения текущих процессов `ps` покажет существование только двух процессов:

```test
    PID TTY          TIME CMD
      1 pts/0    00:00:00 bash
      9 pts/0    00:00:00 ps
```

Используем утилиту pstree xnj,s :

```bash
pstree
```

Результат выполнения операции будет содержать информацию о наличии всего одного процесса в ОС (в отдельном окне терминала ):

```bash
pstree
```

Поскольку контейнер не нуждается в инициализации пользовательских процессов и комплексных средств многозадачности и управления ресурсами (таких как systemd), то при запуске контейнер может сразу выполнять целевую программу.

Выполним эмуляцию целевой нагрузки контейнера выполнив скрипт:

```bash
for i in {001..100}; do sleep $i; echo $i; done
```

В новой консоли выполним проверку запущенных контейнеров:

```bash
docker ps
```

Вывод будет содержать основные сведения о контейнере:

```text
CONTAINER ID   IMAGE     COMMAND   CREATED         STATUS         PORTS     NAMES
655e865433e8   busybox    "sh"    7 minutes ago   Up 7 minutes             busy_cohen
```

Стоит заметить, что поскольку мы не указывали имени контейнера, оно было сгенерировано автоматически.

Указать имя контейнера можно при помощи флага `--name [container_name]` при запуске контейнера.

Можно также отобразить уже остановленные контейнеры:

```bash
docker ps -a
```

Остановленные контейнеры можно удалить при помощи команды:

```bash
docker rm "[container_id|container_name]"
```

Также для автоматического удаления контейнера после остановки (окончания начального процесса) для команды `run` можно добавить флаг `--rm`.

Для того чтобы подключиться к контейнеру при помощи дополнительного виртуального терминала следует выполнить команду:

```bash
docker exec -it "[container_id|container_name]" bash
```

Такое подключение не затронет уже запущенный процесс поскольку будет запущенно в отдельном виртуальном терминале, при этом `pstree` не сможет отобразить процессы между отдельными виртуальными терминалами поскольку у них разные корни.

При этом, второму виртуальному терминалу будет доступна вся файловая система ОС.

Таким образом, например, удобно осуществлять запуск сервисных сценариев комплексных приложений в контейнерах.

Посмотреть текущую нагрузку контейнеров на хост систему можно при помощи команды:

```bash
docker stats
```

Посмотреть процессы контейнера можно при помощи команды:

```bash
docker top
```

Остановим (без удаления) текущий контейнер. Для этого следует завершить все процессы в контейнере или выполнить команду:

```bash
docker restart "[container_id|container_name]"
```

Однако, контейнер автоматически удалится если при запуске был указан флаг `--rm`.

Для повторного его запуска можно использовать команды:

```bash
docker restart "[container_id|container_name]"
# или
docker start "[container_id|container_name]"
```

И затем повторно подключиться к виртуальному терминалу контейнера:

```bash
docker attach "[container_id|container_name]"
```

### Задание 2 | Докеризация приложения

Для контейнеризации приложения следует прежде всего создать `Dockerfile`. Этот файл будет содержать описание подготовки образа контейнера. Файл следует создать в корне проекта.

```Dockerfile
# Используем в качестве основы образ, предназначенный для работы с python
# ‼️ При работе в закрытом контуре МГТУ использовать образ registry.gitlab.bmstu.ru/devops-dataops-intro/labs/lab-2-docker/python:3.12
FROM python:3.12

# Установка зависимостей
COPY requirements.txt /requirements.txt
# ‼️ При работе в закрытом контуре МГТУ добавить флаг -i https://proxpi.gitlab.bmstu.ru/index/
RUN  pip install -r /requirements.txt && \
     rm /requirements.txt

# Создаём рабочую директорию и копируем туда исполняемые файлы
WORKDIR /app
COPY src src

# Команда, используемая для запуска основного процесса
CMD ["python3", "-u", "-m", "src.main"]
```

Подготовка образа выполняется следующей командой:

```bash
docker build . -t myimage

# ‼️ В случае использования MacOS - следует указать платформу сборки
docker build --platform linux/amd64 . -t myimage
```

Где `myimage` - это название образа контейнера (тег образа), а `.` указывает на директорию относительно которой будет выполнена сборка - текущая директория.

Хорошей практикой является уточнение тега: добавление версии приложения через двоеточие. Например, `myimage:1.0.0`, это позволит избавиться от дублирования имён образов контейнеров, что полезно для быстрого изменения версий.

Следует также заметить, что после запуска python кода локально, в директории `src` появилась директория `__pycache__`, которая содержит кеш компиляции питон кода в текст интерпретатора - эта директория в образе не нужна и поэтому добавлена в файл `.dockerignore` - список игнорируемых при копировании

Для запуска образа следует использовать команду:

```bash
docker run -it --name mycontainer --rm myimage
```

#### Следует обратить внимание, что к контейнеру на данный момент невозможно подключиться с хост ОС, при этом в нём не сохранены предыдущие данные

Однако, если выполнит команду:

```bash
docker exec -it mycontainer bash
```

То будет открыта независимый процесс bash в том же контейнере, такая возможность удобна для выполнения дополнительного администрирования из контекста контейнера (например, оперировать данными БД в проектах ruby on rails).

Для публикации образа в сервисе dockerhub следует использовать команду:

```bash
docker push myimage
```

Однако, это потребует авторизации в сервисе dockerhub и создание собственного репозитория, что не будет рассмотрено в настоящей ЛР.

### Задание 3 | Исправление запуска контейнера приложения

Для исправления запуска контейнера приложения следует выполнить команду:

```bash
docker run -it --rm -p 8080:8000 -v $(pwd)/test.db:/app/test.db myimage
```

Здесь:

* `-p 8080:8000` позволит опубликовать порт приложения в хост ОС, при этом порт 8080 хост ОС будет соответствовать порту 8000 контейнера

* `$PWD/test.db:/app/test.db` позволит связать файл БД хост ОС с файлом БД контейнера.

Особенности именования внутренних хранилищ Docker требуют указывать полный абсолютный путь для связывания файлов с Docker (для этого применена переменная окружения `$PWD`).

Стоит учитывать, что несуществующие в хост ОС файлы Docker-ом будут созданы как директории.

## Часть 3 | Лучшие практики докеризации

Простая контейнеризация приложений на данный момент не отвечает требованиям удобства, скорости и безопасности развёртывания.

Поэтому следует добавить прослойку безопасности для старта приложения.

В качестве реверс-прокси предлагается использовать сервис nginx с самоподписанными сертификатами.

### Задание 4 | Добавление реверс прокси

Для обеспечения безопасности, сгенерируем самоподписанные сертификаты при помощи утилиты openssl:

```bash
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -sha256 -days 365 -nodes -subj "/CN=localhost"
```

Описание старта двух контейнеров в рамках единого стека описано в файле `docker-compose.yaml`.

Файл содержит описание сервисов, которые являются контейнерами с заданными подключениями к файловой системе хост ОС, доступные порты и переменные окружения.

Также описаны секреты и конфигурации nginx.

Запуск осуществляется выполнением команды:

```bash
docker compose up
```

При этом, порты, по которым будет доступно приложение можно получить при помощи `docker ps`.

Например, если вывод команды представляет собой:


### Задание 5 | Добавление версионности API

Хорошей практикой является добавление версии реализуемого API - это позволяет чётко определять какие удалённые вызовы или объекты можно получить у приложения.

При оркестрации мы также увидим возможность одновременной работы нескольких вариантов приложения с разными версиями API.

Во-первых, определим переменную окружения для хранения версии API, в `main.py` следует добавить строчки:

```python
PATH_PREFIX = os.environ.gen("PATH_PREFIX", "v1")
```

Для того чтобы убедиться в корректно переданном пути, следует изменить инициализацию программы:

```python
if __name__ == "__main__":
    print(f"Starting... {PORT=}, {PATH_PREFIX=}")
    uvicorn.run(app, host="0.0.0.0", port=8000)
```

А также для **каждого** пути добавить шаблон используемого пути, например:

```python
@app.get(f"/{PATH_PREFIX}/tasks/", response_model=list[schemas.Task])
```

Если после запуска приложения перейти на страницу `http://localhost:8000/docs`, то несложно убедиться что все пути `/tasks` будут содержать префикс `/v1`.

Соберите docker образ приложения с указанием версии, итоговый тег должен иметь вид: `myimage:v1`.

В `docker-compose.yaml` файле укажите тег этого образа для запуска новой версии.

Настроим теперь nginx для возможности работы с версионированным приложением - изменим 52 и 53 строчки в файле `nginx-default.template.config`:

```text
    location /v1 {
        proxy_pass ${PASS_V1};
```

В `docker-compose.yaml` файле следует также изменить переменную окружения `PASS` на `PASS_V1`.

После запуска следует обратить внимание, что `https://localhost:8443/docs` более недоступен - путь `location /v1` проксирует только те запросы, что содержат `/v1` в своём пути, а `/docs` таковым не является.

#### В отчёте следует указать [5]

1. Итоговый текст файлов `main.py`, сервис `tasks` в файле `docker-compose.yaml`

2. Указать запросы curl для работы с версионированным приложением

3. Ответить на вопрос - что следует сделать для того чтобы сделать путь `/docs` снова доступным?

### Задание 6 | Развёртывание второго экземпляра приложения

Работа над заданием выполняется по вариантам

#### Задание для нечётных вариантов

Допустим, заказчик приложения для управления задачами прочитал книжку про RESTfull сервисы, из которой выяснил что v1 версия нашего приложения несколько не соответствует идеальным представлениям.

Следует поменять все пути `/tasks` на `/task` - "всего одну букву убрать" - цитата заказчика.

Однако, мы как опытные инженеры понимаем, что это изменение сломает все старые интеграции и поэтому хотим как можно упростить переход для интегрированных с нами приложений.

Следует реализовать версию `v2` приложения с изменением путей `/task`.

#### Задание для чётных вариантов

Допустим, заказчик приложения для управления задачами решил отказаться от описания задачи (поля `description`) поскольку им никто не пользовался

При этом, следует сохранить старые значения в БД, не возвращать их в новой версии приложения.

Однако, такое изменение очевидно сломает интеграции, которые с нашим приложением сделали уже созданные сервисы, которые опираются на `v1` версию приложения.

Поэтому следует реализовать версию `v2` приложения с изменением схемы данных в интеграции, но не модели БД.

Для изменения схемы данных в интеграции следует удалить поле `description` (строчка 7) в файле `schemas.py` и установить значение по-умолчанию при создании задачи в БД, в файле `crud.py` (строчка 18) установить значение по-умолчанию `description=""`.

#### Общая часть задания

Следует развернуть версию `v2` приложения не взамен, но рядом с приложением версии `v1`, для этого потребуется:

* Собрать отдельный образ v2
* Добавить сервис в `docker-compose.yaml`
* Добавить `location /v2` в `nginx-default.template.config`, проксировать по нему запросы в `PATH_V2`
